# 설계 결정과 이유

이 문서는 "왜 이렇게 했는가"만 모았다. 구현 세부는 [spec.md](../spec.md), 원래 계획은 [plan.md](../plan.md), 샘플 확인 근거는 [notes/sample-check.md](../notes/sample-check.md).

## 1. 왜 학습을 2단계로 나눴나

| | 1단계 | 2단계 |
|---|---|---|
| 시작 가중치 | COCO 사전학습 `yolo26{n,s}.pt` | 1단계 `best.pt` |
| 데이터 | seraphim 35,426장 | DUT + Det-Fly + AOT + AOD-4 + seraphim replay 10,000장 = 38,250장 |
| imgsz / batch | 640 / 32 | 1280 / 8 |
| 목적 | 드론·새·비행기·헬기 구분의 기본기 | 실제 촬영 환경(지상→하늘, 공중→공중) 적응, 작은 드론 |

- **seraphim은 많지만 도메인이 다르다.** 23개 웹 데이터셋을 모은 것이라 양과 다양성은 좋지만 실제 카메라 영상과 분위기가 다르다. 640 패딩 이미지라 해상도를 올려도 이득이 없어서 640으로 빠르게 학습한다.
- **실제 영상의 드론은 작다.** AOT 드론 박스 중앙값은 6px다. 그래서 2단계는 1280으로 올린다(연산량 약 4배, batch는 8로 줄임).
- **replay로 망각을 막는다.** 2단계 데이터만 쓰면 1단계에서 배운 구분 능력을 잊을 수 있어서 seraphim 1만 장을 섞는다.
- **클래스 4개를 두 단계에서 똑같이 쓴다.** 그래서 head까지 그대로 이어받는다. 추론 때는 drone만 보고하지만, 새·비행기·헬기를 따로 학습시켜야 이것들을 드론으로 잘못 잡는 오탐이 줄어든다.

## 2. 왜 프레임이 아니라 영상·장면 단위로 나눴나

연속 프레임은 거의 같은 이미지다. 프레임 단위로 나누면 test에 train과 사실상 같은 이미지가 들어가서 점수가 부풀려진다.

- **Det-Fly**: 시퀀스 정보가 없고 파일 번호도 시간 순서가 아니었다. 원본 train/test 태그도 프레임 단위였다. 그래서 배경 썸네일 유사도로 장면을 직접 묶었다.
  1. 연속 구간: 썸네일 RMS ≤ 2.5인 쌍을 union-find로 연결 → 511개 구간
  2. 장소·세션: 구간 평균 썸네일로 average-linkage 클러스터링, 20에서 자름 → 40개
  3. 장소 병합: 가장 가까운 프레임 쌍 거리 ≤ 18이면 합침 → **20개 장소**
  - 3번은 검토 중에 추가했다. 밝기만 바뀐 같은 세션이 train과 test에 나뉘어 있었다(거리 4.5). 병합 후 test↔train 최소 거리는 18.5다.
- **AOT**: 비행(flight) 단위. 드론 비행은 7개뿐이라(3,662프레임) 나누지 않고 전부 보조 테스트로만 쓴다.
- **AOD-4**: 영상 ID 단위. 같은 정적 카메라로 찍은 같은 세션의 영상은 하나의 그룹으로 합쳤다(125개 그룹 → 28개).
- **DUT**: 시퀀스 ID가 없어서 공식 split을 그대로 썼다. 대신 문제를 측정해서 보고한다(5절).

## 3. 왜 테스트셋을 이렇게 정했나

| 테스트 | 시점 | 이유 |
|---|---|---|
| Anti-UAV300 RGB test 91 시퀀스 | 지상→하늘 (주) | 비교 기준 모델(HF yolov11s)과 같은 세트 |
| Det-Fly 테스트 장면 5개 | 공중→공중 (주) | AOT 드론 데이터가 너무 적어서 이쪽을 주 테스트로 바꿈 |
| AOT 드론 비행 7개 | 공중→공중 (보조) | 초소형 드론, 학습에 쓰지 않은 지역 |
| AOT 오탐 테스트 비행 | 오탐률 | 새·비행기·헬기·빈 하늘에서 drone을 잘못 잡는지 측정 |
| DUT test | 지상→하늘 (참고) | 공식 split이 같은 영상을 공유해서 일반화 지표로는 쓰지 않음 |

- 테스트 데이터는 학습, 검증, 하이퍼파라미터 튜닝, threshold 선택 어디에도 쓰지 않는다. recall·오탐률용 conf threshold도 stage2 **val**에서 정한다.
- Anti-UAV300은 test 시퀀스뿐 아니라 train/val 프레임 전체(약 30만 장)도 누수 대조에 넣었다. 같은 촬영 환경이라 다른 데이터셋에 재업로드된 사본이 섞여 있을 수 있기 때문이다.

## 4. 왜 중복과 누수를 이렇게 제거했나

- **md5 + pHash**: 정확히 같은 파일은 md5로, 리사이즈·재인코딩된 사본은 pHash 해밍 거리로 찾는다.
- **테스트 누수는 보수적으로 지운다** (해밍 ≤ 6, 추가 검증 없음). 잘못 지워도 잃는 것은 학습 이미지 한 장이다. 반대로 놓치면 테스트 점수 전체를 믿을 수 없게 된다.
- **학습 데이터 사이의 중복에는 NCC 검증을 더했다.** pHash는 단색 하늘 이미지를 잘 구분하지 못한다. 회색 하늘의 헬기와 드론이 거리 4~6으로 나와서 AOD-4의 34%가 지워질 뻔했다. 그래서 32×32 흑백 썸네일의 정규화 상관계수가 0.85 이상일 때만 중복으로 본다. 진짜 사본은 약 1.0, 하늘만 닮은 경우는 0.3~0.7이다.
- **같은 그룹 안의 비슷한 프레임은 남긴다.** 한 영상 안의 연속 프레임은 사본이 아니라 시간상 이웃이고, 이미 같은 split에 들어 있다.
- **저작권이 애매한 데이터는 뺐다.** AOD-4의 YouTube 프레임 10,182장과 seraphim 안의 pathikg(유튜브 프레임) 사본 약 43,200장이다.
- **AOD-4의 Anti-UAV 출신 5,298장은 전부 뺐다.** 파일명으로는 모두 train 시퀀스 출신이지만, Anti-UAV300 전체가 테스트 전용 데이터라 같은 촬영 환경의 누수를 피했다.

결과: train/val 119,221장 중 44,171장 제거, 최종 101,697행. 남은 학습 이미지와 테스트 전용 이미지(321,348개 해시) 사이의 md5 일치 0, pHash ≤ 6 일치 0.

## 5. 알고 있는 한계

- **DUT**: train/val 7,800장 중 약 6,100장이 DUT test와 거의 같다. 공식 split이 같은 영상의 프레임을 나눠 가진 것이다. `test_dut`는 오염된 참고 지표로만 본다.
- **Det-Fly**: 한 캠퍼스 주변에서 촬영돼서, 같은 장소를 다른 시간에 찍은 세션은 다른 장소로 남는다. 따라서 Det-Fly test는 "새 지역"이 아니라 "새 촬영 세션"에 대한 일반화를 잰다. 새 지역은 AOT 보조 테스트가 맡는다.
- **pathikg 경계 사례 43장**: pHash는 가깝지만 NCC가 0.85 미만이라 남겼다.
- **시점별 데이터**: 학습용 지상→하늘 드론 이미지는 모두 DUT에서 나온다.
- **early stopping 기준**: Ultralytics fitness는 4개 클래스 전체 기준이고 drone만 보지는 않는다.

## 6. 왜 학습 스크립트를 이렇게 만들었나

- **명령 하나로 시작한다** (`uv run scripts/train.py --model n --stage 1`). 별도 준비 단계가 없다.
- **n과 s는 같은 yaml을 쓴다.** 모델 크기만 다르게 해야 비교가 공정하다. 메모리가 부족하면 두 모델의 batch를 같이 줄인다.
- **정전과 크래시에 대비한다.**
  - 매 epoch `last.pt`를 저장하고, 원자적으로 교체하는 `last_safe.pt` 백업과 5 epoch마다 스냅샷을 둔다.
  - 같은 명령을 다시 치면 읽을 수 있는 가장 최근 체크포인트에서 이어간다. 끝난 run(`done.json`)은 다시 돌리지 않는다.
  - 학습 중에는 절전을 막는다.
- 모두 smoke 학습에서 시험했다: 중간 강제 종료 후 이어하기, `last.pt` 손상 후 `last_safe.pt`로 이어하기, 최종 검증 중 종료.
- **재현 정보**: run마다 `run_info.json`(git commit, split 파일 md5, GPU)을 남긴다.
